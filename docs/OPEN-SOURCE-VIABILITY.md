# CCAW 开源立项审查

日期：2026-10-28（Asia/Shanghai）。范围：公开需求、直接替代方案与现有项目记录的桌面研究。未开展用户访谈、竞品安装验收、付费调用或实际采用实验。

## 决策

**建议停止当前综合平台方向的继续开发，不以“转为开源”作为继续投入的理由；暂不把它缩成另一个额度恢复工具重新立项。**

痛点真实存在，但目前没有足够证据证明目标用户需要再安装一个 CCAW 综合平台。未发现完全相同的组合，不等于没有直接替代，也不构成产品优势。这个判断针对当前投入方向，不是断言所有相关工具都没有需求。

保留现有源码、文档、账本和事故证据。本轮没有修改运行代码、界面、版本、配置或任务身份，没有启动作业、调用模型、提交、推送或发布。本文不把竞争项目的 README 声明当作独立验证结果。

## 需求证据及其限度

在 openai/codex 公开问题中，至少四个不同账号提出额度恢复后继续原任务的需求，本次查询均为 open：

| 原始报告 | 创建时间（UTC） | 可支持的判断 |
| --- | --- | --- |
| [#28931](https://github.com/openai/codex/issues/28931) | 2026-06-18 | App 用户希望长 Goal 在限额恢复后自动继续 |
| [#31386](https://github.com/openai/codex/issues/31386) | 2026-07-07 | 明确要求逐任务启用、沿原 Goal 恢复并保留权限 |
| [#40905](https://github.com/openai/codex/issues/40905) | 2026-08-26 | 报告同一长任务被五小时额度中断两次 |
| [#43605](https://github.com/openai/codex/issues/43605) | 2026-09-07 | 请求持久等待、原任务接续及状态过期时阻断 |

这些是不同账号的公开报告，不是四位经过身份核验的受访者，也不是四个已接受第三方工具的用户。部分讨论存在工具作者的推广；推广与重复评论不能累加为独立需求。问题尚未关闭，也不能单独证明最新产品的全部行为或未来路线。

因此可以确认“人工看守额度窗口”并非个人特例，不能由此推导市场规模、付费意愿、安装意愿，或对多模型路由、经验库、Git 同步和 GUI 整套组合的需求。

## 直接替代与重叠

以下判断来自实际存在的公开仓库及其 README，不代表已经审计、安装或推荐其安全性。

| 项目 | 文档描述的能力 | 对 CCAW 的影响 |
| --- | --- | --- |
| [Codex Auto Resume](https://github.com/progressrdx/codex-auto-resume) | 明确选择桌面任务、等待自然额度恢复、核对后在原会话继续；声明支持 Windows/macOS，并设客户端版本兼容保护 | 额度恢复与原任务接续已有直接同类；客户端适配还会形成长期维护负担 |
| [Continuation Layer](https://github.com/Hsi431/continuation-layer) | 包装官方交互式 Codex CLI，在额度失败后等待并继续原会话；前台监督器有明确运行边界 | CLI 额度接续也不是空白，需要比较真实差异 |
| [Vanth](https://github.com/holdfast-labs/vanth) | 分离执行后台命令，以 SQLite 保存作业及事件，等待有意义事件，唤醒 Codex/OpenCode；描述幂等启动与恢复边界 | 连“长计算脱离聊天、结果出现后再唤醒”这个收缩方向也已有直接重叠 |
| [duet-agent](https://github.com/dzhng/duet-agent) | 分类器选择模型及推理强度、顾问升级、持久状态与长任务等待 | 决策路由加持久编排的组合已有替代，不能把接入 Jev 本身当作优势 |
| [CONTINUUM](https://github.com/Cyrax321/CONTINUUM) | 语义检查点、幂等操作账本、不确定副作用的核对及恢复验证 | 任务恢复与纠错方向已有专门项目，应证明具体缺口而非增加相似模块 |

Vanth 文档中的持久状态，不应被解读为任意计算进程能够跨机器重启继续运行；CONTINUUM 的受控操作账本也不代表能约束任意 shell 命令。竞品存在证明替代方案存在，不证明它们已解决所有场景或已有稳定的大规模采用。

## 为什么当前不值得继续平台化

1. **整合价值未验证。** 原先以个人订阅、模型偏好和工作方式构建的组合，尚没有外部用户证据支撑。目标转向公共项目后，需要重新验证，而不能沿用原先的个人需求作为市场结论。
2. **节省成本与提升效果均未实证。** 没有在相同任务和验收标准下，对照直接使用 Codex及现有工具，测量总模型用量、任务通过率、人工干预、失败恢复及维护时间。增加路由调用、上下文迁移和重试可能抵消便宜模型的单价优势。这是待验证风险，不是已测出的结果。
3. **可靠性承诺比功能组合更难。** 客户端协议、账号状态、权限、进程身份和系统重启均涉及持续维护。事故记录已说明，操作规范与工作目录设置不能替代权限隔离。Git 检查点可提供部分恢复材料，但不能阻止任意路径删除，也不自动覆盖未跟踪数据、凭据或外部副作用。
4. **没有持续验证渠道。** 当前没有经核实的外部试用群体和长期维护承诺。测试数量、文档规模、界面及版本标签都不能填补这一缺口。已经投入的工作不是继续投入的证据。

最强的反对意见是：现有工具分散，Windows 上的可靠运行、安全边界和恢复体验可能仍然存在共同缺口。因此结论允许被新的用户证据推翻，但现在不据此另起一个猜测性的安全或编排平台。

## 允许重启的证据门槛

以下是建议的决策门槛，不是已取得的数据，也不是市场统计标准：

- 至少三位互不相关的目标用户，在尝试相关现有工具后，仍能提供同一种重要缺口的可复现案例。
- 至少两位愿意在真实任务中连续试用两周，并记录人工干预与失败，而不只是表示“有兴趣”。
- 先证明最小改动能减少人工干预；涉及恢复时，必须在真实中断场景中证明会核对执行状态、阻断未知状态重跑，并可撤销自动继续。涉及文件保护时，另外验证实际权限与恢复边界。
- 如果现有项目的补丁或适配器就能满足需求，优先贡献；只有现有架构无法合理容纳这个缺口时，才考虑独立项目。

没有达到门槛，就维持停止开发的建议。这里没有安排继续编码、购买模型订阅、招募用户、联系维护者或公开发布；这些都不是本轮已经完成的工作。
