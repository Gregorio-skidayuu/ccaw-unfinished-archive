# CCAW 产品设计草案 v0.1

日期：2026-10-26（Asia/Shanghai）

状态：设计基准；当前实现和验证范围以 STATUS.md 为准。

定位：以 Codex 为主要执行器，管理模型选择、长任务执行、可恢复进度、工程纠错和工作流更新的个人工具。

## 1. 目标与当前假设

在验收质量不下降的前提下，降低完成任务的总成本；模型、会话或工具升级时，尽量保留已完成工作并从可验证的检查点接续。

本稿先按个人使用、本地优先、单机运行、沿用已有 Plus、不新增付费订阅设计。实际操作系统、预算、项目技术栈和可用模型在实施前确认。编程品味与技术栈规范保留独立配置位置，等待后续补充。

| 需求 | 产品必须提供的行为 |
| --- | --- |
| R1 任务连续性 | 对话或模型中断后，仍可找到任务、计算进程、成果、检查点与下一步 |
| R2 经济性路由 | 每个任务经过轻量分流；脚本、基础对话、便宜模型、主力模型、强模型各有适用条件 |
| R3 持续更新与纠错 | 适配外部变化；将工程错误转化为有证据、有作用范围、可验证和可回退的改进，供后续任务复用 |
| R4 适度工程 | 只实现当前需要的执行、恢复与管理功能；更新机制的维护成本也计入总成本 |

不承诺绕过用量限制、让关闭的计算机继续计算，或保存从未写入持久介质的瞬时状态。连续性目标以已持久化且可验证的工作为边界。

## 2. 用户实际使用流程

1. 输入目标、验收条件和必要约束；默认沿用已设置的预算与项目规范。
2. 产品给出简短执行说明：选择谁、为什么、是否新增费用、如何验收。已授权范围内直接执行，重要歧义才请求输入。
3. 常规修改由 Codex 处理；规则明确的大批量操作交给脚本；模型处理适合其能力的部分。
4. 长计算交给独立运行器；任务页显示“计算中，等待结果”，期间不反复调用模型。
5. 计算完成或失败后，运行器保存事件；有可用额度与预算时自动进入下一阶段，否则显示“等待额度”并保留成果。
6. 完成后交付结果、验证证据和实际开销；有可复用的故障经验时，生成并验证相应纠正措施，供后续相关任务使用。可随时查看为何路由、重试或切换。

示例：修改实验代码 → 启动八小时实验 → Codex 额度耗尽 → 实验继续 → 运行器保存结果 → 在获准的备用模型可用时分析，或等待原额度恢复。接续前检查实验实际状态，不重复启动训练。

## 3. 小型稳定内核与可替换边界

第一版采用模块化单体：一个本地后台服务、SQLite 和文件系统，先提供命令行入口。后台服务由操作系统管理其生命周期；长计算不作为聊天客户端的附属进程。界面以后读取同一任务服务。

| 模块 | 职责 | 明确边界 |
| --- | --- | --- |
| 任务内核 | 状态转换、依赖、接续、取消、去重 | 不包含具体模型排名或价格 |
| 路由策略 | 用规则选择执行方式、模型角色与升级条件 | 不默认增加一次模型调用 |
| 接入适配器 | 启动、接续、取消、接收结果，转换供应商事件与错误 | 不假定所有供应商支持相同能力 |
| 长任务运行器 | 管理独立计算、日志、退出状态与完成事件 | 等待期间无需模型在线 |
| 更新与纠错 | 管理配置版本、故障经验、改进验证和回退 | 未证实的原因不升级为全局规则 |

先定义两个内部边界：AgentBackend 管模型/智能体交互，JobRunner 管计算进程。角色选择不应掩盖工具差异：一个能生成文本的 API 不自动具备 Codex 的文件操作、沙箱或会话恢复能力。

首批接入范围为 Codex、一种经核实可用的低成本 API、确定性脚本，以及人工交接。ChatGPT 基础对话先作为人工辅助入口，导出简短任务包供使用；只有确认可用的官方程序接口后，才把相应步骤纳入自动调度。

## 4. 路由与成本约束

路由顺序为：验收条件 → 数据与权限约束 → 所需工具 → 推理难度与影响范围 → 可用额度与预算 → 历史成功率。先排除不具备必要能力的执行者，再比较成本。

| 角色 | 初始用途 |
| --- | --- |
| SCRIPT | 规则明确的转换、提取、重复检查与计算 |
| CHAT | 解释、需求整理与不依赖项目执行环境的讨论 |
| ECONOMY | 边界明确、可验收、低风险的批量模型工作 |
| DEFAULT | 日常实现、调试与集成，默认由 Codex 承担 |
| EXPERT | 高难度推理、疑难根因与高风险关键审阅 |
| HUMAN | 主观取舍、缺失的事实、必要授权 |

角色映射到账号实际可用的模型和执行环境。上一轮讨论中的具体型号、价格和套餐能力只作为待核实候选，不作为内核常量，也不据此承诺当前账号可以调用。

大工作量不等于高推理难度。人工适合提供判断与授权；不能只为减少 token，把可自动执行的重复劳动转给用户。

模型升级根据验收失败、已定位的能力不足、或继续尝试的预期成本决定。重试分别处理临时网络错误、额度耗尽、接口不兼容与内容错误；每步有有限的重试和升级预算，避免模型之间反复转交。

成本分别记录：新增 API 费用、订阅用量的已知信号、耗时、重试与人工介入。订阅额度不能直接折算成 API 美元成本；获取不到的剩余额度标记为未知并注明来源时间。

API 支出按任务和周期配置限额，派发前预留在途请求的估算费用，结束后对账。价格未知时不自动发起新增付费调用；只有供应端具备并启用硬限额时，才可将其视为对应的计费上限保障。跨供应商接续必须符合已设置的数据访问范围和费用授权。

## 5. 任务与长计算分别记录状态

任务状态与计算状态分开，避免把“AI 正在等待”误认为“计算已停止”。

| 对象 | 建议状态 |
| --- | --- |
| Task | READY、WORKING、WAITING_JOB、WAITING_CAPACITY、WAITING_INPUT、VERIFYING、DONE、FAILED、CANCELLED |
| Job | QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED、UNKNOWN |

任务记录保存目标、验收条件、相关文件、已完成事实、证据位置、未完成事项和下一动作。每次模型执行产生独立 Attempt，记录实际模型、工具版本、规则版本、会话 ID、费用来源与结果。切换模型会新增 Attempt，保留任务身份与既有证据。

Job 保存运行标识、命令、目录、代码与输入版本、运行器任务 ID、启动时间、日志、结果、检查点及退出状态。不能仅凭 PID 判断同一计算仍在运行；需结合启动标识与运行器回执。

启动采用持久化运行意图、唯一执行标识和领取锁；完成事件落盘后再确认消费。同一事件可能重投，消费者必须可去重。无法判断旧作业是否启动成功时进入 UNKNOWN，先核对实际状态，不能盲目重启。涉及外部付费或其他副作用的动作还需对应系统的幂等机制；不能笼统承诺全系统“恰好执行一次”。

短任务使用原生进程等待；长任务由运行器监听退出或读取调度器状态。必要的健康检查由普通程序低频执行，不触发模型。恢复时先核对代码变更、检查点和成果；正常计算的继续运行不依赖 Codex 会话存在。

SQLite 是本机调度状态的唯一写入来源，简短 Markdown/JSON 任务包由其导出，避免多份状态相互覆盖。实验日志与大成果留在文件系统；Git 管代码和规则，凭据与大型检查点不提交到 Git。

## 6. 持续更新的六个独立对象

| 更新对象 | 必备元数据 | 更新办法 |
| --- | --- | --- |
| 模型与账号目录 | 角色、模型 ID、账号范围、调用方式、能力、价格单位、来源、核验时间、有效期 | 配置更新与必要的小额可用性验证 |
| 路由与预算策略 | 版本、适用任务、升级条件、限额、历史样本 | 规则更新并对受影响样本比较 |
| 工程规范 | 版本、作用范围、维护者、来源 | 按项目加载，避免全局规则重复堆积 |
| 纠错经验与回归案例 | 触发条件、证据、原因、范围、纠正措施、验证结果与状态 | 检索相关经验，验证后复用，失效时撤销 |
| 接入适配器 | 支持的客户端版本、接口版本与能力表 | 锁定依赖，接口变更时验证适配器 |
| 内核与数据格式 | schema_version、兼容范围、迁移与备份信息 | 显式迁移，不在未知格式上继续写入 |

模型目录的状态至少区分：未核实、可见、已成功调用、暂不可用、已停用。列在模型列表中不等于账号具有调用权限；一次成功也只证明当次请求可用，后续仍受额度与授权变化影响。

更新配置采用一个可阅读、带版本历史的来源；运行数据库保存其应用记录和快照。developer_instructions 管执行习惯，AGENTS.md 管编码规范，路由/预算配置管模型选择，运行器代码负责等待与恢复。会影响费用、权限和去重的约束必须由程序执行，不能只写成提示词。

每次任务执行锁定实际使用的模型映射、策略、规范与适配器版本。新默认配置用于后续执行；已运行计算保持原代码和参数。模型被下线等情况需要按已授权策略建立新的执行尝试，并记录差异。安全权限撤销和预算停止条件始终即时生效，不能被旧快照绕过。

## 7. 更新与纠错发布闭环

流程：发现变化 → 形成候选差异 → 检查格式与兼容性 → 验证受影响能力 → 在少量任务上试用 → 发布到后续任务 → 观察并保留回退点。

发现变化使用官方变更来源、实际错误与人工输入；缓存结果并按有效期刷新，不为每个任务重新搜索全部供应商信息。新发布或低单价本身不是自动切换的充分理由。

低成本验证优先：纯规则检查、历史事件重放、适配器契约检查，其次才是必要的真实模型调用。更改预算规则无需重跑长实验；适配器升级要验证接续与错误处理；内核状态变更要覆盖中断和恢复。

保留一小组代表性任务：简单修改、局部 Bug、批量处理、跨模块决策与高风险审阅。使用相同验收标准比较成功率、总费用、重试次数与人工耗时。运行中的真实任务不默认并行调用第二个模型做比较。

配置和程序回退时，不回滚用户已完成的代码或重复计算。数据迁移前备份并检查恢复方法；不可逆迁移不能只回退旧程序。必要时保持旧版本只读并提供任务导出。

AI 可在既有授权内自动记录故障、修复代码，并验证和发布局部、可逆的纠正措施；扩大适用范围时需要更强证据和相应验证。提高费用上限或扩大权限仍遵守用户授权。更新系统本身的维护时间、验证调用和故障成本也必须计入评价。

### 7.1 工程纠错闭环

纠错是产品的一等能力：发现失败或用户纠正 → 保存最小必要证据 → 恢复当前工作 → 确认原因 → 形成最小纠正措施 → 验证 → 写入带范围的经验 → 后续相关任务应用 → 观察是否减少复发、是否误伤。

当前问题的修复与后续工作流的改进分别验收。修好代码不等于已防止流程复发；写了复盘也不等于防护已生效。暂时无法定位原因时标记“待确认”，保留恢复办法，不能把猜测当作规则依据。

| 错误类型 | 优先落地的纠正措施 |
| --- | --- |
| 实现缺陷 | 修复对应代码；在有实际保护价值时增加针对性回归用例 |
| 执行与恢复缺陷 | 修正运行器、状态转换、去重或接续协议，并验证故障场景 |
| 路由或能力判断失误 | 更新对应任务特征与升级条件，用同类样本验证；避免一次失败就全面弃用某模型 |
| 需求理解偏差 | 更新已确认的任务约束或项目规范，必要时改进澄清触发条件 |
| 外部服务或环境问题 | 分类处理临时故障、额度与依赖变化，更新适用环境信息或等待策略 |
| 验证方法错误 | 修正测试或验收方法，重新判断原先结论，避免修错产品代码 |

纠正措施优先放在能直接防止错误的代码、运行器或验证环节；需要判断的经验写成按需加载的短规则。没有合理复发可能的一次性小问题，可以只保留任务记录，不强制增加长期规则或测试。

### 7.2 一条经验必须回答的问题

| 字段 | 内容 |
| --- | --- |
| 何时相关 | 项目、环境或版本、任务类型、可观察的触发条件 |
| 发生了什么 | 预期、实际结果、最小日志或 diff，以及可复现证据的位置 |
| 原因有多确定 | 已确认的原因与仍待验证的假设分开记录 |
| 下次如何处理 | 具体操作、自动防护或需要检查的条件；说明不适用的范围 |
| 如何证明改进 | 回归用例、故障重放或其他足以验证此类问题的证据 |
| 目前是否生效 | 候选、已验证、启用、失效或已撤回，以及关联的规则/代码版本 |

经验按根因合并，保留复发次数和最近证据，不把每条失败日志都作为新记忆。SQLite 可保存结构化索引与启用状态，证据文件单独引用；初版使用项目、任务类型和错误特征检索即可。

### 7.3 后续任务如何真正受益

任务开始时，通过项目、执行方式、受影响模块和已知错误特征筛选相关经验。只注入少量匹配的启用规则；确定性的防护由程序执行。失败后则利用具体错误特征再查一次，避免每轮都加载完整历史。

经验先作用于当前任务或项目；有跨任务证据后才扩大范围。用户明确指出的偏好可直接成为相应范围的约束，但不能凭一次局部反馈推断所有项目都适用。撤回的经验停止注入，历史执行保留当时的规则版本以便追溯。

日志、依赖输出和外部文档中的文字只作为待核实数据，不直接变成高优先级执行指令。经验记录不保存凭据，也不默认把项目经验发送给所有模型供应商。

### 7.4 纠错示例：恢复后重复启动实验

假设一次限额中断后，接续智能体误把状态文件缺失当作实验未启动，重复启动了同一训练。

1. 当前修复：识别两次运行与成果，在明确安全或获得相应授权后取消多余计算，保留需要的结果。
2. 原因确认：检查启动回执与状态写入顺序；若确认存在“已启动但未记录”的窗口，把原因定位到启动协议。
3. 流程修正：运行器在启动前记录唯一运行意图，启动后保存回执；恢复先查真实作业，无法确认时进入 UNKNOWN。
4. 验证：在启动与回执之间模拟中断，再恢复并重复投递同一事件，检查不会再启动第二份训练。
5. 后续应用：所有使用该运行器的任务自动获得代码级防护；交接规则只保留“状态未知先核对作业”的必要指引。

如果复发，重新检查根因或防护是否覆盖实际路径；不能只重复追加“不要重复启动”的提示词。

### 7.5 如何评价纠错是否有效

核心指标为同类错误在相关任务中的复发率，并同时观察防护命中、错误阻断、额外耗时和维护成本。错误计数需按任务类型与工作量解释，不能把任务变少造成的失败减少算作改进。

先使用任务本身的验证与本地故障重放，复用已有上下文；常见问题用确定性检查处理。只有根因困难或影响重大时才调用强模型深入审阅，不为每次小失败额外启动完整复盘或全量测试。产品保证的是有证据的纠正闭环，不保证从此不存在同类错误。

## 8. 上下文与后续品味规范

交接包只含：当前目标、约束、已完成事实、相关文件和版本、验证证据、运行中的 Job、尚存的不确定性、下一动作。摘要保留出处，不能替代真实日志和测试结果；不要求保存模型内部推理。

基础规则常驻，技术栈和品味规范按任务加载，当前任务只保留必要上下文。首次接续先读交接包，再按证据扩展阅读。切换供应商前按数据规则筛选文件和日志，不能默认转发整仓库、凭据或完整聊天历史。

并行修改同一代码区需要先解决隔离和合并；v0.1 默认串行写入同一工作区，不先建设多智能体协作平台。

## 9. 实施顺序与验收门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| v0.1 连续性底座 | 单项目、Codex 接入、任务账本、独立计算、重启接续、最小故障记录与导出 | 关闭交互客户端后计算仍运行；运行器重启可核对状态；重复完成事件不导致重复启动 |
| v0.2 低成本路由与纠错复用 | 规则分流、一种低成本 API、预算控制、故障分类、经验检索与局部纠正措施 | 额度耗尽可明确等待或在授权范围内接续；同类后续任务实际应用已验证纠正措施 |
| v0.3 可验证更新 | 配置与经验版本、兼容检查、候选验证、发布、回退与迁移 | 替换模型不改内核；新配置不扰动旧计算；错误规则可撤回且不再注入 |
| v0.4 日常可用性 | 薄控制台、项目规范与按证据增加的第三方接入 | 常见操作无需手工维护状态文件；维护成本可接受 |

版本字段、配置与状态分离、基本备份和任务导出从 v0.1 就要具备；完整更新管理界面可以后做。

首个纵向验证任务：接收一项代码修改 → 启动可控长计算 → 断开客户端 → 恢复服务并核对运行 → 保存结果 → 使用任务包接续分析。同时模拟额度不足，验证不会静默切换到未授权付费通道。

优先确定的开发规格为 Task、Attempt、Job 三类记录，接入能力表、最小运行器协议和角色路由配置。暂不投入微服务、通用插件市场、自动提示词进化或完整聊天界面。

## 10. 已核实的接入事实与待验证项

本节查阅日期为 2026-10-26；文档事实不等于用户账号与安装环境已经验证。

- Codex SDK 支持程序化控制、继续和恢复本地线程；官方将自动化任务与 CI 列为 SDK 使用场景。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)
- App Server 提供会话、审批和事件等深度接入能力；接口与生成 schema 绑定具体客户端版本，部分功能属于实验性能力，应隔离在适配器中。[Codex App Server](https://learn.chatgpt.com/docs/app-server)
- API Key 使用按 OpenAI Platform API 价格计费，不能当作订阅内额度使用。[Authentication](https://learn.chatgpt.com/docs/auth)
- 官方提供经授权的 ChatGPT plan OAuth 与 App Server 接入文档；其中明确模型目录不能当作账号权益检查，实际完成的推理轮次才验证当次访问。[Codex app-server — Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

实施前需核实：个人本地集成适用的登录方式与权限、安装版本、实际可用模型、可获取的额度信号、运行器的持久性、DeepSeek 的当前型号与计费，以及用户 API 预算。未来若对外提供托管或商业产品，需要重新核对适用的授权、接入和数据边界。

当前结论：产品架构可按稳定任务状态、可替换接入、工程纠错闭环与版本化策略设计；具体型号、费用、连续执行能力和纠错效果必须由接入验证、故障演练及后续任务记录建立证据。
